## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: Brand-new interval tasks with a cadence longer than a week can be scheduled too early because the first target date is anchored to the current week, not the task's own interval period.
- Evidence: `internal/scheduler/service.go` `intervalTaskScheduleDates` computes the first target as `startOfWeek(planDate).AddDate(0, 0, offset)` where `offset = taskNameHash(name) % cadence`. For a task with `CadenceValue = 30` and a small hash offset, the target can land within the current week even though the task was just created and should not be due for weeks.
- Recommendation: For interval tasks with no history, derive the first target from `planDate` plus the offset (capped to the interval) so the offset is relative to the task's own cadence, or clamp the offset to the planning horizon.
- Rule candidate: When staggering the first occurrence of an interval-based task, derive the offset from the task's own cadence period rather than an unrelated weekly epoch.

### Finding 2
- Severity: medium
- Category: test-gap
- Summary: No test directly verifies that daily tasks are prioritized ahead of weekly tasks of the same priority under budget pressure.
- Evidence: `taskSortRank` and `cadenceUrgencyRank` were added to make daily work win, but the new `TestSchedulerSpreadsRecurringTasksAcrossWeek` only checks counts and spread; it does not assert that a daily task displaces or precedes a same-priority weekly task when only one fits.
- Recommendation: Add a focused scheduler test with a daily 20-minute task and a weekly 60-minute task of the same priority in a 60-minute budget, then assert the daily task schedules and the weekly task overflows or is deferred.
- Rule candidate: —

### Finding 3
- Severity: low
- Category: test-gap
- Summary: No test exercises the brand-new interval task spreading branch.
- Evidence: All interval-task tests seed a previous completion so the task is due today. The `intervalTaskScheduleDates` path for tasks with no history is not directly covered.
- Recommendation: Add a test that creates two new weekly interval tasks and verifies they are not both scheduled on day 1.
- Rule candidate: —

### Finding 4
- Severity: low
- Category: simplification
- Summary: `taskNameHash` uses a hand-rolled byte-sum instead of a standard library hash.
- Evidence: `internal/scheduler/service.go` defines `taskNameHash` with `h = h*31 + int(name[i])`. This is simple but has uneven distribution and is harder to reason about than `hash/fnv`.
- Recommendation: Replace `taskNameHash` with `hash/fnv` or `hash/crc32` for better distribution and clarity.
- Rule candidate: Prefer standard-library hash functions over ad-hoc string hashing for stable scheduling offsets.
