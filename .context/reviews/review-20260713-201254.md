## Findings
### Finding 1
- Severity: medium
- Category: bug
- Summary: Webhook mode accepts any `TELEGRAM_WEBHOOK_URL` path, but the server only mounts the Telegram handler at `/webhooks/telegram`, so domain-backed webhook deployments can silently configure Telegram to post to an unserved path.
- Evidence: `configureTelegramTransport` in `cmd/server/main.go` calls `bot.SetWebhook(ctx, webhookURL, webhookSecret)` with the full environment-provided URL, but always registers the handler with `mux.Handle("/webhooks/telegram", webhooktg.NewHandler(...))`. There is no validation that `TELEGRAM_WEBHOOK_URL` ends with `/webhooks/telegram`, and no dynamic route registration for other paths.
- Recommendation: Validate that `TELEGRAM_WEBHOOK_URL` uses the served `/webhooks/telegram` path before enabling webhook mode, or derive and register the handler path from the configured webhook URL.
- Rule candidate: When runtime config sets an external webhook URL, validate that the app actually serves the same path or derive the served route from the configured URL.
