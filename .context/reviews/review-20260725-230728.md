## Findings

### Finding 1
- Severity: medium
- Category: test-gap
- Summary: No test proves a task actually falls back to another window when its preferred window is unavailable.
- Evidence: `internal/scheduler/service_test.go` adds `TestSchedulerFitsRealisticCombinations`, but every scenario there fits tasks in their originally preferred window because demand-aware budgeting gives each window exactly the demand it needs. The story verification explicitly states the scheduler should "fall back to other windows when the preferred window is full and the total day budget allows it."
- Recommendation: Add a test where a task’s preferred window is blocked by a calendar event (or already filled) and another window has spare budget, then assert the task schedules in the fallback window.
- Rule candidate: —

### Finding 2
- Severity: low
- Category: simplification
- Summary: `prepareCandidate` and `tryFitInWindow` both compute the same ready-time and gap-shift logic.
- Evidence: `internal/scheduler/service.go` `prepareCandidate` calculates the preferred window’s `readyAt`, then `tryFitInWindow` recalculates `readyAt` from scratch for the preferred window and for every fallback window. The gap-rule and window-shift checks are duplicated.
- Recommendation: Refactor so `tryFitInWindow` accepts a pre-computed `readyAt` for the window it is testing, or extract a shared `readyAtForWindow` helper used by both functions.
- Rule candidate: Avoid duplicating time-window/gap computation between candidate preparation and placement attempts; use a single helper for a given window.

### Finding 3
- Severity: low
- Category: test-gap
- Summary: Demand-aware budgeting with calendar-blocked windows is not exercised.
- Evidence: The new `splitWindowBudgets` demand-aware path distributes leftover minutes to unblocked windows, but there is no test showing behavior when a window with demand is also blocked by a calendar event.
- Recommendation: Add a scheduler test where total demand fits the daily budget but one preferred window is blocked, and verify tasks either fall back or honestly overflow without crashing the budget math.
- Rule candidate: —

### Finding 4
- Severity: low
- Category: bug
- Summary: Fallback window order is fixed as morning → afternoon → evening, which can place an evening-preferred task into morning even when afternoon has room.
- Evidence: `fallbackWindows` in `internal/scheduler/service.go` always returns the preferred window first, then the other windows in morning/afternoon/evening order regardless of the preferred window.
- Recommendation: Order fallback windows by proximity to the preferred window (e.g., preferred → next later windows → earlier windows) so evening tasks prefer afternoon over morning when afternoon is available.
- Rule candidate: When falling back from a preferred time window, prefer the nearest window before jumping to a distant one.
