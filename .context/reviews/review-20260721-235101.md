## Findings

### Finding 1
- Severity: low
- Category: dead-code
- Summary: Unused helper `taskNamesForOccurrences` remains in `cmd/server/onboarding.go`.
- Evidence: `func taskNamesForOccurrences(items []occurrences.Occurrence) []string` is defined but never called in the file or elsewhere.
- Recommendation: Delete the function to reduce noise.
- Rule candidate: Remove helper functions that have no callers before merging.

### Finding 2
- Severity: medium
- Category: test-gap
- Summary: No automated tests cover the new onboarding endpoints, session store, or task replacement logic.
- Evidence: `cmd/server/onboarding.go`, `internal/tasks/service.go` (`ReplaceTaskWithSubtasks`, `CreateTaskFromStarterTemplate`), and the onboarding routes in `web/src/routes/onboarding/` have no corresponding test files. Manual QA was performed, but regressions in invite-code validation, profile save, task CRUD, and finish scheduling are not protected.
- Recommendation: Add backend table-driven tests for the onboarding handler and service methods, and at minimum one frontend component/render test for the task editor and review page.
- Rule candidate: New backend handlers and service methods must ship with unit or integration tests.

### Finding 3
- Severity: low
- Category: simplification
- Summary: Health and readiness handlers were duplicated in `cmd/server/main.go` after the `internal/app` server was bypassed.
- Evidence: `cmd/server/main.go` now contains inline `GET /healthz` and `GET /readyz` handlers that mirror the logic previously in `internal/app/app.go`. The `internal/app` import was removed entirely.
- Recommendation: Reuse `app.NewServer` for health/ready routes or extract a shared helper so the two implementations do not diverge.
- Rule candidate: Avoid duplicating health/readiness endpoint logic; reuse the application server setup.

### Finding 4
- Severity: medium
- Category: workflow
- Summary: Global CORS is configured with `Access-Control-Allow-Origin: *` for all routes.
- Evidence: `withCORS` in `cmd/server/main.go` sets `*` unconditionally. This is convenient for local development but is a security regression if the same configuration reaches production.
- Recommendation: Make the allowed origin(s) configurable via `WEB_ORIGIN` and default to the frontend dev URL instead of `*`.
- Rule candidate: Production-bound HTTP handlers must not use wildcard CORS; origins must be configurable.

### Finding 5
- Severity: low
- Category: bug
- Summary: Some onboarding endpoints return `400 Bad Request` for authentication/authorization failures instead of `401 Unauthorized`.
- Evidence: `handleCreateTaskFromTemplate`, `handleCreateTask`, `handleUpdateTask`, `handleDeleteTask`, and `handleFinish` call `requireUserSession` and return `http.StatusBadRequest` when the session is missing or the profile has not been saved. The session check itself maps to `401`, but the profile-not-saved branch also returns `400`.
- Recommendation: Distinguish malformed input (`400`) from missing/invalid session or missing profile (`401`).
- Rule candidate: Authentication and pre-condition failures should return `401` or `403`, not `400`.

### Finding 6
- Severity: low
- Category: bug
- Summary: Frequency labels use awkward pluralization for singular values.
- Evidence: `formatTaskFrequency` in `web/src/lib/api/onboarding.ts` renders "Every 1 day(s)" and "1 time(s) each week".
- Recommendation: Special-case `1` to render "Every day" and "1 time each week".
- Rule candidate: User-facing count labels should use grammatically correct singular/plural forms.

### Finding 7
- Severity: low
- Category: simplification
- Summary: Onboarding task-by-ID routing uses manual path parsing instead of Go 1.22 pattern strings.
- Evidence: `handleTaskByID` trims `/onboarding/tasks/` manually and sets `r.PathValue("taskID")` because the original root handler conflicted. The root handler conflict was resolved, so pattern-based registration is now possible.
- Recommendation: Simplify to `mux.HandleFunc("PUT /onboarding/tasks/{taskID}", ...)` and `mux.HandleFunc("DELETE /onboarding/tasks/{taskID}", ...)`.
- Rule candidate: Use standard framework routing patterns when they are available.
