## Findings

### Finding 1
- **Severity:** low
- **Category:** simplification
- **Summary:** The OAuth callback page redefines `apiBaseUrl` locally instead of importing it from `$lib/api/onboarding.ts`, creating a second source of truth for the backend URL.
- **Evidence:** `web/src/routes/onboarding/calendar/callback/+page.svelte` defined its own `const apiBaseUrl = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8080';`.
- **Recommendation:** Export `apiBaseUrl` from `onboarding.ts` (or a shared API config module) and import it in the callback page.
- **Rule candidate:** Keep API base URL configuration in a single exported constant.

### Finding 2
- **Severity:** medium
- **Category:** test-gap
- **Summary:** The new calendar step and OAuth callback pages have no unit/page tests. Existing review and telegram pages have at least basic tests.
- **Evidence:** New files `web/src/routes/onboarding/calendar/+page.svelte` and `web/src/routes/onboarding/calendar/callback/+page.svelte` had no accompanying `.test.ts` files.
- **Recommendation:** Add minimal page tests covering unavailable state, connected state, and callback error/success handling (mocking `fetch` for the callback).
- **Rule candidate:** New route components should include at least a smoke test.

### Finding 3
- **Severity:** low
- **Category:** test-gap
- **Summary:** Backend tests verified `calendar_connected` is false after disconnect and that the service reports connected, but no handler test asserted the state endpoint returns `calendar_connected: true` when a connection exists.
- **Evidence:** `cmd/server/onboarding_test.go` had `TestOnboardingCalendarDisconnect` checking false; service tests checked true; no state-endpoint true case.
- **Recommendation:** Add a test that seeds a connection, calls `/onboarding/state`, and asserts `calendar_connected` is true.
- **Rule candidate:** —

### Finding 4
- **Severity:** low
- **Category:** simplification
- **Summary:** Each onboarding page hardcoded its "Step N" label, which became brittle after inserting the calendar step. The stepper already derives step numbers from the steps array.
- **Evidence:** `web/src/routes/onboarding/calendar/+page.svelte` used "Step 4 · Recommended", `tasks/+page.svelte` used "Step 5 · Required", etc.
- **Recommendation:** Derive the label from the step object (e.g., `formatStepLabel(steps[N])`) or remove the hardcoded label in favor of the stepper.
- **Rule candidate:** Derive step labels from the canonical steps array.

### Finding 5
- **Severity:** low
- **Category:** simplification
- **Summary:** Every time a not-yet-connected user loaded the calendar step, `handleCalendarStatus` generated a new OAuth state row. Unconsumed states expire after 15 minutes, but repeated refreshes created unnecessary rows.
- **Evidence:** `cmd/server/onboarding.go` `handleCalendarStatus` called `calendarService.GoogleAuthURL` unconditionally when not connected.
- **Recommendation:** Reuse a recent pending OAuth state for the same user/session instead of generating a new row on every calendar page load.
- **Rule candidate:** —

### Finding 6
- **Severity:** low
- **Category:** bug
- **Summary:** When calendar was not connected, the review page told the user "You can connect it later from settings." No settings page/route existed yet.
- **Evidence:** `web/src/routes/onboarding/review/+page.svelte` previously said: "You skipped the calendar step or it was not available. You can connect it later from settings."
- **Recommendation:** Change copy to avoid referencing settings until it exists.
- **Rule candidate:** —
