## Findings

### Finding 1
- Severity: medium
- Category: test-gap
- Summary: The new calendar-aware day-selection test only exercises interval tasks; count-based tasks use a different date-selection path that is not covered.
- Evidence: `internal/scheduler/service_test.go` `TestSchedulerCalendarAwareDaySelection` seeds `CadenceTypeInterval` tasks with an afternoon block. The `countTaskScheduleDates` function has its own `chooseBestDates` call and `candidatePool` construction, but no test verifies that a count task moves away from a blocked day.
- Recommendation: Add a subtest for a count-based task (e.g., a 2x/week task) whose default day is blocked and which should move to a lighter day within the same week.
- Rule candidate: Every distinct cadence path that changes scheduling behavior must have a dedicated regression test.

### Finding 2
- Severity: low
- Category: simplification
- Summary: `PlanDay` and `previewDayWithOccurrences` load calendar blocks for the plan date twice, and `loadCalendarConstraintsForRange` issues one DB query per day.
- Evidence: `internal/scheduler/service.go` lines 67 and 74 both fetch blocks for `planDateStr`. `loadCalendarConstraintsForRange` then loops `start..end` calling `s.blocks.ListByUserAndDate` for each day, resulting in seven round-trips for every planning call.
- Recommendation: Add `CalendarBlockRepository.ListByUserAndDateRange(ctx, userID, startDate, endDate)` and load the whole horizon in a single query. Derive the plan-date `calendarConstraints` from that result instead of querying separately.
- Rule candidate: When a service needs constraints for a date range, load them in one repository call rather than N+1 calls per day.

### Finding 3
- Severity: low
- Category: test-gap
- Summary: Day-selection reasons are computed and returned in `PlanResult.Reasons`, but no test or endpoint currently proves the user will see them.
- Evidence: `/schedule/plan` returns the full `PlanResult` JSON, including `Reasons`, but `web/src` has no references to `Reasons`, and `cmd/server/lookahead.go` only consumes `BlockedWindows` and `SmallTaskOnlyReason`. The verification criterion says "The schedule explanation can tell the user why a task landed on a particular day."
- Recommendation: Either add a test that asserts `Reasons` are populated in the API response for a moved task, or wire the reasons into the existing schedule explanation (e.g., `/schedule/plan` web page or `/lookahead`).
- Rule candidate: When a feature adds user-facing explanatory data, include an automated test that demonstrates the data reaches the response or UI contract.

### Finding 4
- Severity: low
- Category: simplification
- Summary: `availableBudgetScore` hardcodes the total available window minutes (13 * 60) instead of deriving it from the window definitions.
- Evidence: `internal/scheduler/service.go` `availableBudgetScore` computes `max(0, 13*60-blocked)`. The same file already has `windowDurationMinutes`, which knows morning=240, afternoon=240, evening=300.
- Recommendation: Compute the baseline as the sum of `windowDurationMinutes` for the known windows so the scoring logic stays consistent if window durations ever change.
