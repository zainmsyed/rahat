## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: Onboarding confirmation message shows the wrong calendar date for users in timezones behind UTC.
- Evidence: `internal/notifications/telegram/service.go` `buildOnboardingConfirmationText` formats `planDate.In(loc).Format("Monday, January 2")`. `planDate` is the UTC-midnight instant returned by `localDateAsUTC`, not the user's local midnight. For `America/Chicago` (UTC-5/6), 2026-07-25 00:00 UTC is 2026-07-24 in local time, so the message says "Friday, July 24" instead of "Saturday, July 25".
- Recommendation: Build the date label from `plan.Date` parsed in the user's location (e.g., `time.ParseInLocation("2006-01-02", plan.Date, loc)`) instead of converting the UTC `planDate` instant.
- Rule candidate: When displaying a persisted local calendar date to a user, parse the canonical date string in the target timezone rather than formatting a UTC-midnight instant.

### Finding 2
- Severity: medium
- Category: bug
- Summary: Confirmation message displays misleading exact ready times because `ReadyAt` is computed from fixed UTC window hours.
- Evidence: `buildOnboardingConfirmationText` renders `item.Occurrence.ReadyAt.In(loc).Format("3:04 PM")`. The scheduler sets `ReadyAt` from `daytime.StartTime(planDate, window)`, which uses 08:00/12:00/16:00 UTC. For `America/Chicago` this converts to 03:00/07:00/11:00 AM, so "morning" tasks are shown at 3:00 AM.
- Recommendation: Either omit exact ready times from the Telegram summary and rely on the window name (morning/afternoon/evening), or make the scheduler timezone-aware before rendering localized clock times.
- Rule candidate: Do not render localized clock times that are derived from timezone-agnostic UTC boundaries unless the underlying scheduler is timezone-aware.

### Finding 3
- Severity: medium
- Category: test-gap
- Summary: No handler-level test proves onboarding remains successful when the Telegram confirmation fails.
- Evidence: `cmd/server/onboarding_test.go` has tests for linked, unlinked, and duplicate cases, but no test uses a failing bot and asserts HTTP 200 + session cookie + `telegram_delivered=false`. The failure path is only covered at the service layer.
- Recommendation: Add a handler test that makes `fakeTelegramBot.SendMessage` return an error, calls `/onboarding/finish`, and verifies the response succeeds, the session cookie is set, and `telegram_delivered` is false.
- Rule candidate: —

### Finding 4
- Severity: low
- Category: simplification
- Summary: `windowOrder` helper duplicates existing logic in `internal/time/windows.go`.
- Evidence: `internal/notifications/telegram/service.go` defines a private `windowOrder` function that maps "morning"/"afternoon"/"evening" to 0/1/2. The same mapping already exists as `daytime.Order`.
- Recommendation: Import `github.com/rahat/rahat/internal/time` as `daytime` and reuse `daytime.Order(window)` in the sort comparison.
- Rule candidate: Reuse existing domain helpers instead of redefining order/mapping functions.

### Finding 5
- Severity: low
- Category: bug
- Summary: Review page may report the wrong Telegram delivery status if the user linked Telegram after the page loaded.
- Evidence: `web/src/routes/onboarding/review/+page.svelte` uses `state.telegram_linked` from the initial state load to choose between "delivered", "failed", and "not linked" copy. If the user links Telegram in another tab and returns without refreshing, `state.telegram_linked` is stale and the UI may claim Telegram wasn't linked even though the confirmation was delivered.
- Recommendation: Use `finishResult.telegram_delivered` as the primary signal for the success/failure copy and only fall back to `state.telegram_linked` to explain why no message was sent.
- Rule candidate: Derive post-action status from the action response, not from stale client state captured before the action.

### Finding 6
- Severity: low
- Category: test-gap
- Summary: `OnboardingConfirmationRepository` has no direct unit tests.
- Evidence: The repository in `internal/store/onboarding_confirmation.go` is exercised only through `SendOnboardingConfirmation` service tests. Edge cases like `Get` with a malformed `sent_at`, `Record` with empty user ID, and idempotency behavior are not directly verified.
- Recommendation: Add a small repository test that creates a record, fetches it, and verifies duplicate `Record` calls are ignored.
